# 테스트 전략 — TDD 기본

> **이 프로젝트의 기본 개발 방식은 TDD다.** 모든 기능은 테스트를 먼저 쓰고(Red) → 통과시키고(Green) → 정리한다(Refactor).
> **러너는 Jest(jest-expo).** RN 1차 지원 — 실제 RN 트리 렌더 + 네이티브 모듈 모킹 내장으로 가장 효율적.

## 왜 TDD

- 인수조건을 **실행 가능한 명세**로 고정 → 회귀를 자동으로 막는다.
- 구현 전에 인터페이스(계약)를 먼저 설계 → 경계면 버그가 줄고 설계가 단순해진다.
- 리팩터링(예: 컨벤션 정합화) 시 안전망이 된다.

## Red → Green → Refactor

1. **Red** — 인수조건 하나를 표현하는 **실패하는 테스트**를 먼저 작성한다(`npm test`로 빨강 확인).
2. **Green** — 그 테스트를 통과시키는 **최소 구현**.
3. **Refactor** — 초록 유지하며 중복 제거·컨벤션 정합화.

> 한 번에 하나의 작은 인수조건씩 사이클을 돈다. 큰 덩어리를 한꺼번에 구현하지 않는다.

## 테스트 스택 (Expo SDK 52 / RN 0.76)

- **러너/프리셋**: `jest` + `jest-expo` 프리셋 (RN 1차 지원, 실제 RN 렌더 트리).
- **컴포넌트/훅**: `@testing-library/react-native`(v12+, jest matchers 내장) — `render`, `screen`, `fireEvent`, `renderHook`.
- **타입**: `@types/jest`.
- 파일명: 소스 옆 콜로케이션 `*.spec.ts` / `*.spec.tsx`(대표 심볼명 기준, 컨벤션 §네이밍).
- 명령: `npm test`(=`jest`), watch는 `jest --watch`.

## 무엇을, 어느 깊이로 테스트하나

| 대상 | 테스트 | 비고 |
|------|--------|------|
| **순수 유틸**(`code.ts`, `errors.ts`) | ✅ 단위 필수 | 입력→출력, 경계값(혼동문자·길이·토큰 매핑). ROI 최고 |
| **커스텀 훅**(`useCreateRoom/useJoinRoom/useMembership`) | ✅ `renderHook` + **supabase 모킹** | 상태 전이(loading/success/error), 계약 매핑(snake→camel), 에러 토큰→메시지 |
| **화면/컴포넌트**(`OnboardingScreen` 등) | ✅ `render` + 상호작용 | 분기(step)·입력 정규화·성공/실패 UX. 무거우면 핵심 흐름 위주 |
| **네비 분기**(AuthGate/MembershipGate) | △ 상태별 렌더 단위 | 네비 컨테이너는 모킹 |
| **SQL/RPC/RLS/트리거** | ❌ 단위 대상 아님 | 실 DB 필요 → 스모크. 클라 측은 모킹된 응답/에러로 계약 검증 |
| 외부 SDK(Supabase·Kakao·expo-*) | ❌ 직접 테스트 안 함 | **모킹**. 우리 코드의 호출/매핑/처리만 |

## 모킹 원칙

- `@/lib/supabase`의 `supabase`를 모킹해 `rpc`/`from().select()...` 반환을 제어(성공·에러·shape).
- 외부 라이브러리의 동작이 아니라 **우리 코드가 그것을 어떻게 부르고 결과를 처리하는지**를 검증한다.
- 네이티브 동작(Kakao Map, 실 세션/DB, 제스처)은 단위 대상 아님 → **디바이스 스모크**(사용자 환경).

## 좋은 테스트 (오버피팅 금지)

- 인수조건/행동을 검증한다. 내부 구현 디테일(호출 순서 등)에 과결합하지 않는다.
- 경계값·실패 경로를 반드시 포함(빈 입력, 잘못된 코드, 네트워크 실패, 정원 초과 등).
- 단언이 "load-bearing"이어야 한다 — 깨야 할 때 실제로 빨개지는지 표본 확인(껍데기 단언 금지).

## 테스트를 거는 위치 — 공개 경계(seam) 사전 합의 (guksu-harness 1.18)

테스트는 **합의된 공개 경계(seam — 호출자가 쓰는 인터페이스)** 에 쓴다: 유틸의 export 함수, 훅의 반환 계약, 화면의 사용자 가시 동작(텍스트·접근성·핸들러 효과), RPC/Edge Function의 응답 shape(모킹 경계). 구현 내부(사적 함수·내부 상태·스타일 상수)에 결합된 테스트는 리팩토링마다 깨져 유지비만 남긴다. **어느 경계를 지킬지는 스프린트 plan에서 인수조건과 함께 합의해 기록**하고, qa-logic은 테스트가 그 경계에 걸려 있는지도 본다.
