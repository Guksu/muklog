# 하네스 절대 규칙 — 정본 (muklog)

이 파일이 muklog 하네스 절대 규칙의 **단일 출처**다. CLAUDE.md·오케스트레이터·에이전트 정의는 규칙 전문을 복제하지 않고 이 파일을 포인터로 참조한다("작업 전 `docs/harness-rules.md`를 읽는다"). 복제본은 반드시 드리프트한다 — 규칙 수정은 이 파일 한 곳에서만 한다.

이 파일은 **작업하는 쪽이 매 작업 전에 읽는다** — 그래서 여기 있는 것은 작업 중에 지켜야 할 것뿐이다. 규칙은 늘리지 않는다: 새 제약은 먼저 훅·deny로 기계화할 수 있는지 보고, 도메인 한정이면 규칙이 아니라 해당 스킬에 넣는다(guksu-harness v2.0 원칙).

규칙 1(git)·6(시크릿)의 실제 강제 수단은 산문이 아니라 **훅**이다(blockGitMutation·blockSecretAccess·branchGuard). 이 문서는 에이전트가 이유를 이해하기 위한 요약이다.

> 출처: [guksu-harness](https://github.com/Guksu/guksu-harness) v2.1.0 `harness-rules.md` 정본을 muklog에 맞게 적용(규칙 8·9는 muklog 고유). 정본이 갱신되면 이 파일을 다시 동기화한다.

1. **git 작업은 사용자 전담.** commit·push·merge·branch 삭제를 에이전트가 수행하지 않는다. 종료 시 "커밋은 직접 진행하세요"로 안내만 한다. 예외 2종(모두 사용자 승인 기반): ① 사용자 확인된 브랜치 전환은 `git switch(-c)`로만. ② 사용자가 명시 요청한 커밋·PR 업로드(`allowCommitPush` 옵트인, 스프린트마다 feat 브랜치→완료 시 PR). 이때도 커밋 메시지·PR 본문에 Claude 작성 표기(Co-Authored-By 등)는 절대 넣지 않는다 — 훅이 기계적으로 차단한다. merge·rebase·force push·브랜치 삭제·PR 머지는 예외 없이 사용자 전담. **브랜치 이름은 `feat/`·`fix/`·`docs/`·`chore/` 등 컨벤션 프리픽스만 — `claude/` 등 에이전트 자동 생성 프리픽스 절대 금지**(사용자 지시 2026-08-20).

2. **코드를 생성하면 TDD가 기본.** 인수조건 = 테스트 케이스(Red→Green→Refactor), 종료 기준에 `npm test` 전체 통과 + `tsc --noEmit` 포함. 외부 인프라(SQL·RPC·외부 SDK·네이티브)는 모킹/스모크로 분리(`docs/testing-strategy.md`). 테스트는 계획 문서에 기록된 **합의된 공개 경계(seam — 호출자가 쓰는 인터페이스)** 에 쓴다 — 구현 내부에 결합된 테스트는 리팩토링마다 깨져 유지비만 남긴다. 어느 경계를 지킬지는 스프린트 계획(plan)에서 합의해 기록한다.

3. **작업 산출물과 기록을 구분한다.** 역할 간에 주고받는 작업 산출물(plan·ui-spec·dev-notes·QA 리포트)은 `_workspace/{slug}/`에 쓰고 읽는다 — 이번 작업 동안만 살고 커밋되지 않는다(gitignore). **보존되는 기록은 `docs/history/` 문서 하나뿐이다: PR 하나 = 문서 하나.** 작업이 끝나면 흐름을 끝까지 본 쪽(오케스트레이터 리더)이 `_workspace/` 산출물을 근거로 하나로 종합해 `docs/history/{YYYY-MM-DD}-{slug}.md`(템플릿 `docs/templates/history.md`)에 남긴다. 역할마다 각자 기록을 남기면 같은 작업이 여러 문서로 흩어져 어느 것이 전체인지 알 수 없다. 기록 없는 push는 blockGitMutation의 기록 게이트가 차단한다. (2026-09-01 이전 기록은 `docs/sprint/{slug}/` 5문서 체계 — 감사 추적으로 보존, 새 작업은 이 규칙을 따른다.)

4. **단일 출처 문서를 따른다.** 설계 `docs/design/architecture.md` · 코드 컨벤션 `docs/code-convention.md` · 테스트 전략 `docs/testing-strategy.md` · **UI 비주얼은 킷 `templates/muklog`**(`.claude/skills/ui-design/templates/muklog/`) · UX 원칙(킷이 침묵하는 영역만) `ux-principles` 스킬. 어긋나면 임의 판단하지 말고 사용자에게 확인한다.

5. **QA는 경계면 교차검증 + incremental + 2축 분리 보고.** 존재 확인이 아니라 생산자(쿼리/RPC/Edge Function)↔소비자(훅/화면)를 동시에 읽고 shape을 비교한다. 전체 완성 후 1회가 아니라 모듈 완성 직후마다. 자기가 만든 것을 자기가 검증하지 않는다 — 같은 맹점을 공유한다. 결과 보고는 **컨벤션 축**(code-convention 위반)과 **스펙 축**(plan/계약 위반)을 별도 절로 나누고 합산 순위를 매기지 않는다 — 한 축의 발견이 다른 축을 가리는 것을 방지한다.

6. **시크릿은 읽지도 기록하지도 않는다.** `.env`·credential·키 파일을 읽지 않고, 산출물·로그·보고에 토큰/키/비밀번호를 옮겨 적지 않는다. 기록은 보존되는 파일이므로(규칙 3) 기록된 시크릿은 곧 유출이다. 설정값이 필요하면 키 이름만 언급한다.

7. **출력은 읽는 사람이 이해할 수 있게 쓴다.** 질문·보고·문서 등 사용자에게 보이는 모든 출력에 적용한다. 전문용어는 써도 되지만 처음 나올 때 한 줄로 풀이하고, 한 문장에는 하나의 내용만 담고, 약어·영문 용어를 풀이 없이 나열하지 않는다. 어렵게 쓴 글은 사용자의 결정을 늦추고 답변의 질을 떨어뜨린다.

8. **비용폭탄 회피 최우선 (muklog 고유).** 백엔드는 Supabase 무료 티어 안에서만 운영하고 AWS 리소스를 쓰지 않는다. 폴링·상시 연결·타이머 재확인을 만들지 않는다(콜드스타트 1회 원칙). 신규 외부 API 호출은 계획 단계에서 호출 수 상한을 명시한다.

9. **1 스프린트 = 1 기능 (muklog 고유).** 여러 기능을 한 스프린트로 묶지 않는다. 같은 화면·같은 성격의 소항목 묶음(예: 피드백 3종)은 한 기능으로 본다. 기능이 스프린트보다 크면 분할해 첫 조각만 진행한다.
