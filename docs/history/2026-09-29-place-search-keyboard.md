## 1. 개요

장소 검색 화면은 들어오자마자 키보드를 띄우는데, 결과 목록에는 키보드 여백이 없었다. 그래서 iOS에서 키보드가 열린 동안 아래쪽 결과("카페" 15건 중 12~15번째)를 볼 수 없었다. 이 문제는 메모 키보드 수정(#33)의 로직 QA가 범위 밖 항목으로 찾았다. 이번 작업은 디자인 킷(`templates/muklog/mk-log.jsx` 502행)의 "키보드가 열리면 목록 아래에 키보드 높이만큼 여백" 동작을 React Native로 옮겼고, 먹로그 에디터와 위시리스트 추가 검색 두 곳에 함께 적용된다.

## 2. 작업 내용

기획 → 에디터 테스트 수정(개발)과 킷 매핑 문서 작성(퍼블리싱)을 병행 → 선택자 교체가 끝난 뒤 검색 화면 테스트·구현(퍼블리싱) → 독립 검증 2종(로직·비주얼, 병행) → 리더 시뮬레이터 확인 → QA 지적 반영 → 로직 재검증 순서로 진행했다.

- `src/features/muklog/PlaceSearchView/PlaceSearchView.tsx` — 결과 목록 `ScrollView`에 `automaticallyAdjustKeyboardInsets={Platform.OS === 'ios'}`를 더했다. `Platform` import와 이유 주석 2줄 외에는 바꾸지 않았다.
  - 이 prop은 키보드가 가린 높이만큼 스크롤 영역 끝에 여백(inset: 스크롤 영역 크기는 그대로 두고 콘텐츠 끝에 덧붙이는 공간)을 넣는다. 키보드가 닫히면 여백을 되돌린다. React Native 기본 기능이며, 메모 수정(#33)과 같은 방식이다.
  - 검색 입력란은 목록 밖(화면 위쪽 머리 영역)에 있다. 그래서 iOS 네이티브 스크롤 뷰는 목록의 스크롤 위치를 바꾸지 않고 여백만 넣는다.
  - 여백은 키보드 애니메이션과 같은 시간·곡선으로 움직인다. 킷의 `.3s` 전환에 해당한다.
  - Android에서는 끈다(`false`). Android는 키보드만큼 앱 창을 줄이는 기존 방식(adjustResize)을 그대로 쓴다.
  - 타이머·반복 확인·키보드 높이 추정·키보드 이벤트 구독·신규 의존성·신규 API 호출은 없다.
  - 공개 props(`PlaceSearchViewProps`)는 바뀌지 않았고, 두 사용처(`MuklogEditor.tsx`, `LogScreen.tsx`)도 고치지 않았다.
  - 두 사용처 모두 검색 화면을 화면 전환 애니메이션(`SwapTransition`) 하나로만 감싼다. 키보드 회피용 감싸개(`KeyboardAvoidingView` 등)가 없어서 여백이 두 번 들어가지 않는다.
- `src/features/muklog/PlaceSearchView/PlaceSearchView.spec.tsx` — 키보드 여백 테스트 8개를 더했다.
  - K1(6개): iOS에서 여섯 상태 모두 여백 기능이 켜진다. 여섯 상태는 검색 전, 검색 중, 결과 15건, 0건 + 직접 입력, 오류 + 직접 입력, 결과 15건 + 제출 중이다. 킷은 상태와 무관하게 여백을 둔다.
  - 각 행은 그 상태가 실제로 그려졌는지 먼저 확인한다. 이름과 다른 상태로 통과하는 것을 막기 위해서다.
  - "제출 중"은 위시를 담는 동안의 상태이고 `LogScreen`만 넘긴다. 이 행은 로직 QA 지적으로 추가했다.
  - K2: Android에서는 `false`다(`undefined`가 아님).
  - K3: 키보드가 열린 채 첫 탭으로 결과를 고르게 하는 기존 설정(`keyboardShouldPersistTaps="handled"`)을 회귀 방지용으로 잠근다.
  - 결과 목록은 컴포넌트 종류로 찾는다(`UNSAFE_getByType(ScrollView)`). 운영 코드에 테스트 전용 식별자를 더하지 않기 위해서다.
  - 나란히 있는 ScrollView가 하나 더 생기면 이 조회가 예외를 던진다.
  - 안쪽에 중첩된 ScrollView는 조회되지 않는다. 그래서 prop을 안쪽 ScrollView로 잘못 옮기면, 조회는 여전히 바깥 ScrollView를 잡고 prop 값을 확인하는 단언(테스트의 기대값 검사)이 실패해서 실수가 드러난다. 중첩 ScrollView를 더하기만 하면 테스트는 그대로 통과한다.
  - spec 주석(`PlaceSearchView.spec.tsx:222-223`)은 처음에 "2개 이상이면 예외"라고만 적었다가, 로직 QA 지적을 받아 위 내용으로 고쳤다.
  - 새 묶음은 기존 "직접 입력" 눌림 피드백 묶음(A10) 앞에 두었다. A10은 "동작 줄이기" 설정을 가짜 함수(목)로 바꿔 두는데, 이 목이 테스트 뒤에 원래대로 돌아오지 않는다. 새 묶음을 그 뒤에 두면 act 경고가 3건에서 64건으로 늘었다. act 경고는 React 테스트 도구가 기다려 주지 않은 시점(act 밖)에 일어난 화면 갱신을 알리는 경고이고, 통과·실패 판정에는 영향이 없다.
- `src/features/muklog/MuklogEditor/MuklogEditor.spec.tsx` — 에디터 키보드 테스트가 폼 스크롤 영역을 찾는 기준(선택자)을 바꿨다.
  - 바뀌기 전: "자동 여백 prop이 있는 ScrollView". 바뀐 뒤: "메모 입력란을 품은 ScrollView". 두 플랫폼 반복 테스트도 같은 기준을 쓴다.
  - 테스트 수(75)와 운영 코드(`MuklogEditor.tsx`)는 바뀌지 않았다.
  - 이유: 검색 화면에도 같은 prop이 생기면, 옛 기준은 검색 상태에서 검색 화면 목록을 폼으로 잘못 잡는다.
  - 로직 QA가 옛 기준을 되돌린 사본으로 확인했다. 그 사본에서 에디터 테스트 1건("메모 포커스 상태로 장소검색에 들어가면…")이 실패했다.
- `docs/ux/ux-backlog.md` — 후속 과제 2건을 등록했다. U69는 키보드가 열린 채 끝까지 내렸을 때 마지막 행 아래 58pt 편차, U70은 검색 입력 안내 문구가 킷과 다른 점이다(4절). main이 표 끝에 U68을 추가했기 때문에, 병합 충돌을 피하려고 표 끝이 아니라 U54 뒤에 넣었다. 이 표는 우선순위순이라 위치가 어긋나지 않는다.
- 공용 UI 패턴 라이브러리 조회(`feSkills.mjs find`)를 두 번 실행했다. 키보드 여백 패턴은 없었다. 1순위 후보(`search-suggest`, 웹 자동완성)를 읽었지만 채택하지 않았고, 코드도 가져오지 않았다.
- 기획·UI 계약·구현 기록·QA 리포트·전후 캡처는 `_workspace/sprint-20260928-place-search-keyboard/`에 있다. 이 폴더는 커밋하지 않으며 작업이 끝나면 폐기한다.

**판단 요약**(인계물 폴더는 폐기되므로 여기에 남긴다)

| 항목 | 결정 |
|------|------|
| 수정 방식 | 네이티브 prop 하나로 해결했다. 키보드 상태 구독·타이머·키보드 높이 추정을 쓰지 않는 것은 스프린트 계획의 가드레일로 정했다. 그중 반복 확인 타이머 금지는 `docs/harness-rules.md` 규칙 8(폴링·상시 연결·타이머 재확인 금지)에 근거한다. 구독 방식은 계획에서 범위 밖으로 뺐고, 도입하려면 이 가드레일과 충돌해 사용자 승인이 먼저 필요하다. |
| 에디터 테스트 기준 | "메모를 품은 스크롤 영역"으로 정했다. 테스트 식별자를 다는 안은 채택하지 않았다. 에디터 테스트는 "스크롤 함수가 폼 스크롤 영역에서 불렸는지"를 컴포넌트 객체끼리 비교해 확인한다. 테스트 식별자로 찾으면 그 객체를 얻을 수 없어 결국 종류로도 찾아야 하므로, 운영 코드에 식별자만 늘고 얻는 것이 없다. |
| 작업 순서 | 에디터 선택자를 먼저 바꾼 뒤 검색 화면 prop을 넣었다. 반대 순서면 중간에 에디터 테스트가 깨진다. |
| 마지막 행 아래 여백 | 키보드가 열린 채 끝까지 내리면 마지막 행 아래 빈 공간이 58pt다. 리스트 아래 패딩 24pt와 안전 영역(홈 인디케이터처럼 기기가 가리는 화면 아래 34pt)을 더한 값이다. 킷은 24px다. 이번 방식(prop 하나)으로는 없앨 수 없어 "알려진 편차"로 두었다. 키보드 구독 없이 줄일 후보 해법이 있지만 추론이라 확인이 필요하다. 백로그 U69로 등록했다(4절). |

## 3. 검증 결과

**용어.**
- Red / Green: 구현 전에 새 테스트가 실패하는 것을 확인하고(Red), 구현 뒤 통과하는 것을 확인하는(Green) 테스트 우선 개발 순서다.
- suites / tests: 테스트 파일 수 / 테스트 개수다.
- 스크래치패드: 저장소 밖의 세션 전용 임시 폴더다. 여기서 만든 사본은 저장소에 영향을 주지 않는다.
- 뮤테이션: 코드를 일부러 망가뜨린 사본(뮤턴트)으로 테스트가 그 변화를 잡아내는지 보는 확인이다. 테스트가 실패하면 "잡힘", 통과하면 "생존"이다.
- 동치 뮤턴트: 코드는 다르지만 겉으로 드러나는 동작이 같은 변형이라, 생존하는 것이 정상이다.
- 모든 뮤테이션은 src를 고치지 않았다. jest가 원본 대신 사본 파일을 읽도록 모듈 경로를 바꿔 끼워 돌렸다.

## 5. 주의사항

- 이 브랜치(main 반영 전)의 워크트리에서는 테스트를 `npx jest --testPathIgnorePatterns '/node_modules/' '/supabase/' '<rootDir>/\.claude/'`로 돌려야 한다.
  - 옵션 없는 `npm test`와 작업 종료 검증 훅(verifierGate)은 경로 문제로 "No tests found"를 내며 실패한다. 코드 문제가 아니다.
  - main을 반영하면 옵션 없이도 돈다.
- 여백 기능은 키보드 크기가 바뀐다는 알림이 올 때만 여백을 계산한다. 키보드가 열린 동안 목록의 크기나 위치가 바뀌어도 여백은 다시 계산되지 않고, 다음 키보드 알림이 와야 맞춰진다.
- 지금은 검색 입력란이 목록 밖에 있어 여백 기능이 스크롤 위치를 건드리지 않는다. 앞으로 입력란을 목록 안으로 옮기면, 포커스된 입력란이 키보드에 가려질 위치일 때 네이티브가 그 입력란을 키보드 위로 올리려고 스크롤 위치도 바꾼다.
- 에디터 키보드 테스트는 "메모 입력란이 폼 스크롤 영역 안에 있다"는 전제에 기댄다.
  - 메모를 스크롤 영역 밖으로 옮기면 테스트가 실패한다.
  - 그때는 메모 키보드 동작도 다시 설계해야 하므로 실패하는 것이 맞다.
- 접근성 "동작 줄이기"와 그 하위 설정 "크로스 페이드 전환 선호"를 켠 사용자는 키보드를 닫을 때 목록이 맨 위로 돌아갈 수 있다.
  - React Native 기본 동작이다. 이 설정에서 키보드 끝 높이가 0으로 오면 스크롤 위치를 맨 위로 되돌린다(`RCTScrollView.m:358-366`).
  - 코드로 확인했고, 시뮬레이터로는 확인하지 않았다.
  - 이 화면에는 이번에 새로 생긴 동작이다. 에디터 폼에는 #33부터 있었다. 막지 않았다.
- 기기 부하가 높을 때는 전체 테스트가 무관한 테스트에서 5초 시간 초과로 실패할 수 있다. 실패한 파일을 따로 돌려 보고 판단한다.
- `.claude/hooks/verifierGate.state.json`은 종료 검증 훅이 스스로 갱신하는 파일이라 변경으로 잡힌다. 이번 코드와 무관하다.
- 추적되지 않는 `.agents/`·`.codex/`·`AGENTS.md`도 이번 작업과 무관하다. 커밋에 넣지 않는다.
