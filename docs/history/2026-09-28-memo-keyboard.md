# 메모 입력란이 키보드에 가려지는 문제 수정

| 항목 | 내용 |
|------|------|
| 날짜 | 2026-09-28 |
| 브랜치 | fix/memo-keyboard-visibility |
| PR | https://github.com/Guksu/muklog/pull/33 |
| 관련 경로 | src/features/muklog/MuklogEditor/MuklogEditor.tsx, src/features/muklog/MuklogEditor/MuklogEditor.spec.tsx |

## 1. 개요

먹로그 작성·편집 화면에서 iOS 키보드가 열리면 메모 입력란과 커서가 키보드 뒤에 가려졌다. 9월 24일과 28일의 시뮬레이터 점검에서 같은 증상이 두 번 재현됐다. 디자인 킷(`templates/muklog/mk-log.jsx`)은 키보드 높이만큼 아래 여백을 두고(399행), 메모에 포커스하면 폼을 맨 아래로 스크롤하도록(454행) 정해 두었는데 앱에는 이 동작이 빠져 있었다. 이번 작업은 그 두 동작을 React Native로 옮겨, 키보드가 열려도 메모 박스 전체가 보이게 했다.

## 2. 작업 내용

수정은 세 단계로 진행했다. 1단계만으로는 부족하다는 것을 시뮬레이터에서 확인해 2단계를 더했고, 독립 QA가 찾은 가장자리 결함을 3단계에서 고쳤다.

- `src/features/muklog/MuklogEditor/MuklogEditor.tsx`
  - **1단계: 키보드 여백 자동 확보.** 폼 스크롤 영역에 `automaticallyAdjustKeyboardInsets`(키보드가 열리면 스크롤 영역 아래에 키보드 높이만큼 여백을 넣고, 닫히면 되돌리는 React Native 기본 기능)를 iOS에서만 켰다. Android는 화면 자체가 키보드만큼 줄어드는 기존 방식(`adjustResize`)을 그대로 쓰므로 켜지 않았다.
  - **2단계: 메모 박스 전체 노출.** 1단계의 기본 기능은 키보드가 열리는 순간 "커서가 있는 한 줄"만 키보드 바로 위에 맞춘다. 그래서 메모 4줄 박스의 나머지는 키보드 뒤에 남고, 이어서 입력하는 줄도 보이지 않았다. iOS에서 키보드 표시 완료 이벤트(`keyboardDidShow`)를 구독하고, 메모에 포커스가 있을 때만 폼을 맨 아래로 스크롤하게 했다. 메모 포커스 여부는 입력란의 포커스·블러 이벤트로 기록하고, 화면이 사라지면 구독을 해제한다. 킷은 포커스 310ms 뒤에 스크롤하는 타이머를 쓰지만, 앱에서는 타이머 대신 키보드 이벤트 한 번에 반응하게 했다. 타이머·반복 확인·키보드 높이 추정·신규 의존성은 추가하지 않았다.
  - **3단계: 장소 검색 왕복 뒤 잘못 스크롤하는 문제 수정(QA 발견 D1).** 메모에 포커스한 채 "장소 검색하기"나 "변경"을 누르면 폼이 통째로 검색 화면으로 바뀐다. 이때 React Native는 사라지는 입력란의 블러 이벤트를 부르지 않아서 "메모에 포커스 있음" 기록이 남았다. 그 결과 폼으로 돌아온 뒤 메모에 포커스가 없어도 키보드가 뜨면 폼이 맨 아래로 스크롤될 수 있었다. 검색 화면을 여는 함수(`openSearch`)에서 기록을 먼저 지우도록 고쳤다. 같은 단계에서 코드 컨벤션에 맞게 리스너(`scrollFormToEnd`)와 정리 함수(`stopRevealingMemo`)에 이름을 붙이고, 스크롤 영역 주석을 2단계 이후 동작에 맞게 고쳤다.
- `src/features/muklog/MuklogEditor/MuklogEditor.spec.tsx` — 키보드 회피 테스트 9개를 추가했다.
  - 여백 자동 확보: iOS는 켜짐, Android는 꺼짐(2개).
  - 메모 포커스 중 키보드 표시 시 폼 맨 아래로 스크롤 — 기본 화면과, 실제 앱 구성(편집 모드 + 장소 검색 연결, 메모 입력 뒤)(2개).
  - 스크롤하지 않아야 하는 경우 — 메모에 포커스가 없을 때, 메모 블러 뒤, 메모 포커스 상태로 장소 검색에 다녀온 뒤(3개).
  - Android는 구독하지 않음(1개). 구독은 1건뿐이고 입력으로 다시 그려져도 늘지 않으며 화면이 사라지면 해제됨(1개).
  - 키보드 이벤트는 실제 앱처럼 이벤트 발신기(`DeviceEventEmitter`)로 보낸다. 처음 구현한 테스트는 가짜 리스너 목록을 직접 호출해서, 구독 직후 바로 해제해 기능이 죽은 코드도 통과시키는 약점이 있었다(QA 발견 T1). 테스트 구성은 독립 QA의 제안을 거의 그대로 반영했다.
- 공용 UI 패턴 라이브러리 조회(`feSkills.mjs find`)를 세 번 실행했다. 키보드 회피와 맞는 후보가 없어 직접 구현했다(반환된 후보는 캐러셀·무한 스크롤 등 무관한 패턴).
- 기획·UI 계약·구현 기록·QA 리포트는 `_workspace/memo-keyboard/`에 있으며 커밋 대상이 아니다.

**3단계 수정 뒤 시뮬레이터 재확인은 하지 않았다.** 재확인하려던 시점에 시뮬레이터 화면이 마지막으로 둔 상태와 달라져 있어서, 병렬로 진행 중인 다른 세션(장소 검색 키보드 확인 작업)이 쓰는 중으로 판단했다. 3단계는 검색 진입 시 기록 초기화 한 줄과 이름 부여·선언 위치 이동뿐이라 주 경로 동작은 바뀌지 않았고, 실제 앱 구성 테스트로 보완했다.

**테스트 실행 환경 참고.** 작업 도중 병렬 세션이 `.claude/worktrees/` 아래에 자체 `node_modules`를 가진 워크트리를 만들었다. 그 뒤로 메인 트리에서 jest를 돌리면 워크트리 쪽 mock과 react-native 사본을 읽어 스위트가 시작 전에 실패했다(`Invariant Violation: __fbBatchedBridgeConfig is not set`). 그래서 이후 모든 실행에 `--modulePathIgnorePatterns '<rootDir>/\.claude/'`를 붙였다. 기존 설정이 테스트 수집에서 이미 `.claude/`를 빼고 있으므로 같은 범위를 모듈 해석에도 적용한 것이다. 설정 파일은 이번 PR에서 바꾸지 않았다. 또 옵션 위치를 잘못 적은 한 번의 실행(병렬 세션 시작으로 부하가 높던 시점)에서 이번 변경과 무관한 `AuthProvider — 부트스트랩 › 세션 없음 → unauthenticated` 테스트가 1회 실패했다. 해당 spec을 5회 다시 돌려 모두 24/24 통과했고 이후 전체 실행도 통과해, 재현되지 않은 일시적 실패로 기록만 남긴다.

## 4. 확인 필요 · 후속

- **3단계 수정 뒤 시뮬레이터 재확인 (담당: 에이전트 또는 사용자).** 시뮬레이터가 비면 확인한다. 순서: 새 먹로그 → 메모 탭(키보드 표시, 메모 전체 보임) → 키보드가 열린 채 "장소 검색하기" → "검색 취소" → 메모 다시 탭 → 메모 전체가 다시 보이는지.
- **Android 실기기 확인 (출시 전, 담당: 사용자).** Android는 이번에 코드를 바꾸지 않았고 단위 테스트로 "iOS 전용 동작이 적용되지 않는다"만 확인했다. 실제로 키보드가 열릴 때 메모가 보이는지는 실기기에서 확인해야 한다. 가려진다면 별도 수정으로 다룬다.
- **iOS 실기기 확인 (출시 전, 담당: 사용자).** 시뮬레이터에서만 확인했다. 시뮬레이터의 앱 바이너리는 9월 12일에 만든 Dev Client(표시 버전 0.1.0)이고, 자바스크립트만 최신이다.
- **별도 작업으로 분리한 것.** 이번 PR 범위가 아니어서 수정하지 않았다(1 스프린트 = 1 기능).
  - 닉네임 변경 대화상자가 접근성 도구에 버튼 하나로 묶여 보이는 문제(`src/components/RenameDialog/RenameDialog.tsx` 카드 `Pressable`) — 별도 세션에서 진행 중.
  - 장소 검색 결과 목록에 키보드 여백 처리가 없는 문제(QA 발견, 킷 `mk-log.jsx:489`·`502` 대비 `PlaceSearchView.tsx`) — 별도 세션에서 진행 중.
  - jest 설정에 `.claude/` 모듈 경로 제외 추가(위 실행 환경 문제) — 별도 작업 제안으로 남김.
  - 알림 설정 "새 먹로그 알림" 설명의 마지막 글자 "요"만 다음 줄로 내려가는 문제 — 미착수, 기능 영향 없음.
- **같은 시뮬레이터 점검에서 확인하지 못한 항목.** 서버 저장·편집·실패 재시도, 현재 위치 이동, 사진 핀치·스와이프, 새 Google 로그인, 실제 푸시, 오프라인 상태. 출시 후보 검증 때 다룬다.

## 5. 주의사항

- 1단계와 2단계는 함께 있어야 한다. 1단계가 만드는 아래 여백이 없으면 2단계의 "맨 아래로 스크롤"이 키보드 위까지 올라가지 못한다.
- 메모에 포커스가 있을 수 있는 상태에서 폼을 화면에서 내리는 새 경로를 만들면, 3단계처럼 포커스 기록을 직접 지워야 한다. React Native는 사라지는 입력란의 블러 이벤트를 부르지 않는다.
- 폼 맨 아래에 새 필드를 추가하면 "맨 아래로 스크롤"의 도착 지점이 달라진다. 메모 아래에 내용이 많이 늘면 메모가 화면 위로 밀려날 수 있으니 그때는 메모 위치 기준 스크롤로 바꿔야 한다.
- 키보드 테스트는 React Native의 jest 모의 구현에 기댄다(모의 ScrollView는 키보드 이벤트를 구독하지 않고, `scrollToEnd`는 공유 모의 함수다). React Native 업그레이드로 이 모의 구현이 바뀌면 테스트가 실패로 드러나므로 그때 함께 고친다.
- 시뮬레이터에서 도구로 글자를 입력하면 하드웨어 키보드 입력으로 들어가 화면 키보드가 닫히고, 반영도 몇 초 늦다. 키보드 관련 확인은 화면 키보드의 키를 직접 눌러서 해야 한다(메뉴 I/O → Keyboard → Toggle Software Keyboard).
- 시뮬레이터 점검 중 이전 점검이 남긴 저장 전 초안(빈 줄과 글자 하나)은 코드 수정에 따른 화면 새로고침으로 사라졌다. 이후 입력한 내용은 모두 확인용이며 저장하지 않고 폐기했다. 이 과정에서 늦게 반영된 입력이 화면 키보드를 닫아, 키보드 키를 노린 탭이 방문일 행에 떨어져 초안의 방문일이 바뀐 적이 있다. 저장하지 않은 초안에서만 일어난 일이다.
