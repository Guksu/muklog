## 1. 개요

초대코드 입력 화면(온보딩 → 코드로 참여하기)의 6칸 입력이 화면 읽기 기능(VoiceOver·TalkBack처럼 화면 내용을 소리로 읽어 주는 기능)에서 입력란으로 보이지 않았다. iOS 시뮬레이터의 접근성 트리(화면 읽기 기능이 보는 요소 목록)를 확인하니, 코드 영역은 이름과 역할이 없는 요소 하나였다. 글자를 입력하면 그 요소의 이름이 "A B"(셀 글자를 이어 붙인 값)가 됐다.

원인은 두 가지였다.
- 셀을 탭하면 숨김 입력란에 포커스를 주는 `Pressable`이 기본값으로 접근성 요소다. 그래서 iOS가 그 안의 숨김 입력란과 셀을 하나로 합쳤다.
- 숨김 입력란이 투명도 0이다. 그래서 합침을 풀어도 iOS가 입력란을 트리에서 뺐다(실험으로 확인, §3).

두 원인을 함께 고쳐 "초대코드" 입력란 하나로 노출되게 했다. 화면 모습과 탭 동작은 바꾸지 않았다.

같은 계열의 선례는 대화상자 카드 접근성 수정(`dialog-card-a11y`)이다. 이 작업 도중 그 작업이 `origin/main`에 머지됐다(#41, `50a03d4`). 그 기록의 후속 후보에 이 파일(`CodeInput.tsx:32`)이 올라 있었다.

진행 순서: 증상 실측 → 소스 조사(워크플로) → 변인 분리 실험 → TDD 수정 → 기기 재측정 → 독립 QA 1차 → 지적 반영(판 2) → 기기 재측정 → 재검증 → 지적 반영(판 3, 테스트·주석·문서만) → 최종 확인.

**이 문서에서 쓰는 말**
- 새 아키텍처 / 구 아키텍처: React Native의 새 렌더러(Fabric)와 옛 렌더러(Paper). 시뮬레이터의 개발용 앱은 새 아키텍처로, 스토어 빌드는 구 아키텍처로 돈다(`app.json` `newArchEnabled: false`).
- 평탄화: 레이아웃만 담당하는 뷰를 실제 네이티브 뷰로 만들지 않는 최적화. 새 아키텍처와 Android에만 있고, iOS 구 아키텍처에는 없다.
- 호스트 요소: 테스트 렌더 트리에서 실제 네이티브 뷰가 되는 노드(`View`·`Text`·`TextInput`).
- AXPress: 접근성 API로 요소를 "누르는" 동작. VoiceOver의 두 번 탭과 같은 경로인지는 확인하지 않았다.
- 변이 검사: 소스를 일부러 망가뜨려 테스트가 실패하는지 보는 검사. 실패하지 않고 통과하면 "생존 변이"라 부르고, 테스트의 빈틈이다.

## 2. 작업 내용

- **`CodeInput.tsx` — 감싸는 `Pressable`**: `accessible={false}`와 `focusable={false}`를 줬다.
  - `accessible={false}`: iOS가 자식(입력란·셀)을 하나로 합치지 않게 한다. Android에서는 이 값이 `setFocusable(false)`가 되어 포커스 항목에서 빠진다(`ReactViewManager.java:89-91`).
  - `focusable={false}`: Android에서 클릭 리스너를 떼고 clickable을 끈다(`ReactViewManager.java:343-347`). 두 값이 함께 있어야 Android에 이름 없는 항목이 남지 않는다.
  - 손가락 탭은 JS 응답 체계(React Native가 터치를 JS 쪽 핸들러로 넘기는 경로)로 처리돼 이 값들의 영향을 받지 않는다.
  - 셀을 탭하면 숨김 입력란에 포커스를 주는 `onPress`와 눌림 피드백 미부여(motion-press-c 주석)는 그대로 뒀다. 대화상자 선례처럼 `View`로 바꾸면 탭 포커스가 사라진다.
- **`CodeInput.tsx` — 숨김 `TextInput`**: `accessibilityLabel="초대코드"`와 `caretHidden`을 주고, 스타일에 `opacity: 0.005`(상수 `HIDDEN_INPUT_OPACITY`)와 `color: 'transparent'`를 줬다.
  - 이름은 앱 표기에 맞췄다. 화면 제목이 "초대코드 입력"이고, 앱 안에 띄어 쓴 "초대 코드" 표기는 없다. 요청 예시는 "초대 코드"였다. 두 표기의 발음 차이는 없을 것으로 보지만, 음성으로 확인하지는 않았다.
  - `aria-label`이 아니라 `accessibilityLabel`이어야 한다. RN 0.76의 `TextInput`은 `aria-label`을 네이티브로 넘기지 않는다. 테스트 도구는 둘 다 맞춰 줘서 jest로는 구분되지 않으므로, spec이 prop 이름까지 잠근다.
  - 투명도 조건은 **0보다 크고 0.01보다 작게**다.
  - 0이면 화면 읽기 기능이 입력란을 뺀다. iOS는 실측했다(§3 실험 A·B). Android도 같은 판정일 것으로 추정한다.
  - 0.01보다 크면 새 아키텍처 iOS의 터치 판정(`RCTViewComponentView.mm:602`, `alpha < 0.01`이면 제외)에 입력란이 들어간다. 그러면 셀 사이 틈·가장자리 탭을 입력란이 직접 받아 커서가 글자 사이로 옮겨질 수 있다.
  - 처음(판 1)에는 0.01을 썼다. 새 아키텍처는 투명도를 소수점 정밀도가 낮은 float로 저장해서, 0.01은 0.0099999998이 되어 겨우 제외된다. QA가 이 경계 문제를 지적했다. 앱 밖 UIKit 탐침으로 저장값(0.010 → 제외, 0.011 → 수신)을 확인했고, RN의 판정 조건은 소스로 확인했다. 반올림에 기대지 않도록 판 2에서 0.005로 낮췄다.
  - 글자색 투명과 커서 숨김은 낮은 투명도로 글자가 희미하게 그려지는 것을 없앤다. 실험 B(투명도 0.01, 글자색 기본)에서는 687픽셀이 최대 3/255만큼 달랐다(눈에는 안 보이는 수준). `'transparent'` 키워드는 `Button`·`IconButton`·`SegmentControl` 등에서 이미 쓰는 방식이다(테마에 투명 토큰이 없다).
  - Android 입력란 밑줄은 원래 그려지지 않는다. RN 0.76 `TextInput`의 기본값이 `underlineColorAndroid = 'transparent'`다(`TextInput.js:1782`).
  - 킷(`mk-home.jsx:249`)은 입력란을 투명도 0으로 둔다. RN에서는 투명도 0.005 + 글자색 투명 + 커서 숨김으로 번역했다. 근사 허용이며, 사유는 RN iOS에서 투명도 0이면 화면 읽기에서 빠지기 때문이다. 결과 픽셀은 같다.
- **`CodeInput.tsx` — 시각 셀 6개**: 셀마다 `accessibilityElementsHidden`(iOS)과 `importantForAccessibility="no-hide-descendants"`(Android)를 줬다. 글자가 따로따로 읽히지 않게 한다. 두 속성을 함께 쓰는 방식은 기존 `MapPrewarm`과 같다.
  - 행이 아니라 셀마다 둔 이유: 셀은 원래 배경·보더 때문에 네이티브 뷰라, 틈을 덮는 새 뷰가 생기지 않는다. 새 아키텍처에서는 셀 글자 뷰가 셀 안으로 들어가는 차이만 있고, 틈 탭 대상과 픽셀은 같다.
  - 행에 두면 새 아키텍처와 Android에서 평탄화되던 행이 네이티브 뷰로 새로 생긴다. 그 행이 셀 사이 틈의 탭을 가로챈다.
  - Android는 지금 그 틈 탭을 입력란이 직접 받는다. RN의 Android 터치 대상 판정이 투명도를 보지 않기 때문이다(소스 기준 추정).
  - iOS 구 아키텍처(스토어 빌드)는 평탄화가 없어 행이 원래 네이티브 뷰다. 그래서 틈 탭은 수정 전후 모두 행 → `Pressable` → 포커스로 간다(소스 기준). 판 1 기록에는 "스토어 빌드는 틈 탭을 입력란이 직접 받는다"고 적었는데, QA 지적으로 정정했다.
  - 실험 C(§3)의 `pointerEvents="none"`은 쓰지 않았다. iOS에서는 입력란이 원래 탭을 받지 않아 효과가 없고, Android의 틈 탭 경로를 바꿀 수 있다.
- **`CodeInput.tsx` — 주석**: 파일 머리에 접근성 구조를 한 번 요약하고, 각 변경 지점에는 이유를 한 줄씩 적었다. 첫 줄 경로 주석을 실제 위치로 고쳤다(모듈별 폴더 이관 때 남은 옛 경로).
- **`CodeInput.spec.tsx`** — 총 21건. 기존 4건 가운데 2건은 셀 조회 범위만 조정했고, 신규는 17건이다.
  - **핵심 인수조건 직접 단언(6건)**: 값이 빈 상태·"AB"·"ABCDEF" 세 상태에서, 코드 영역의 화면 읽기 항목이 입력란 하나뿐인지 본다. 두 플랫폼은 숨김 속성을 다르게 읽으므로 iOS 기준과 Android 기준으로 따로 판정한다.
    - iOS 기준: `accessibilityElementsHidden`만 숨김으로 본다.
    - Android 기준: `importantForAccessibility`만 숨김으로 보고, `focusable` 래퍼도 항목으로 센다.
    - 두 판정 모두 근사다. 검사 범위는 입력란과 셀을 함께 품는 가장 가까운 호스트 요소다.
  - **iOS 조상 사슬**: `origin/main`의 공용 헬퍼 `findAccessibleAncestors`로 입력란을 감싸는 접근성 요소가 없는지 본다(main의 `docs/testing-strategy.md` "접근성 단언" 규정).
  - **나머지 신규**: 라벨 조회와 prop 이름 · 입력란 자신이 접근성 요소 · 입력란은 숨김 아님 · 입력한 값 전달 · 셀 숨김 · 셀마다 iOS·Android 속성 각각 · 투명도(자신 0 초과 0.01 미만, 감싼 조상 투명도 0 없음) · 글자색 투명과 커서 숨김 · 글자가 제자리 셀에 있고 글자부터 루트까지 `display:none`이 아님 · 셀 탭 → 포커스 요청.
  - 투명도·글자색·커서 단언은 스타일 값에 거는 테스트다. 원칙상 피하는 쪽이다. 하지만 테스트 도구(RNTL)는 투명도 0을 숨김으로 보지 않고 터치 판정도 흉내 내지 못한다. 그래서 이 단언이 기기 퇴행을 막는 유일한 잠금이다. 이유를 spec 주석에 적었다.
  - 기존 "6개 셀 렌더"·"글자 표시" 2건은 셀이 의도적으로 숨겨져 기본 조회에서 빠진다. 그래서 `includeHiddenElements: true`만 붙였고, 단언 내용은 그대로다. 이 때문에 약해진 "화면에서 사라짐" 검출은 신규 `display:none` 검사가 대신한다.
- **`src/test/findAccessibleAncestors/`(3파일)**: 이 브랜치의 기준(`6923c0c`)에는 없어서, `origin/main`의 파일을 `git show origin/main:…`으로 바이트 단위까지 같게 가져왔다(sha256 일치 확인). main을 합칠 때 같은 내용이라 충돌하지 않는다.
- **fe-skills 조회(구현 전)**: `otp-input` 후보의 SKILL.md를 읽었다. 칸마다 입력란을 두는 구조라 킷(숨김 입력란 1개 + 시각 셀)과 달라 구조는 쓰지 않았다. "라벨 없는 입력란은 이름 없이 읽힌다 → 이름을 준다"는 판단만 적용했다. 출처: https://github.com/Guksu/fe-skills (fe-ui/otp-input, MIT).
- **조사(워크플로 1회, 에이전트 6)**: RN 0.76.9 소스(iOS 구·새 아키텍처, Android, 테스트 도구)와 외부 자료를 병렬로 조사하고 종합했다. 핵심 결론:
  - UIKit은 자신이나 조상 중 투명도가 0 이하인 뷰를 접근성 순회에서 뺀다(시뮬레이터 런타임 바이너리 분석).
  - RN은 두 아키텍처 모두 투명도를 입력란 바깥 래퍼에 건다. 그래서 안쪽 입력란이 이 규칙에 걸린다.
  - 숨김 입력란을 쓰는 코드 입력 라이브러리들도 투명도를 0보다 조금 크게 두고, 글자색 투명·커서 숨김을 함께 쓴다. 다만 그들은 입력란이 탭을 직접 받게 하려고 0.015~0.02를 쓴다. 이 화면은 기존 탭 경로를 지키려고 0.01 미만을 쓴다.

**미검증**

- 좌표 탭(셀·셀 사이 틈·가장자리를 손가락처럼 누르기). 시뮬레이터 제어 도구의 기기 사용 허락 요청에 응답이 없어 하지 못했다. 대신 jest(셀 누름 → 포커스 요청)로 잠갔다. 새 아키텍처 터치 판정 경계는 소스와 앱 밖 UIKit 탐침으로 확인했다.
- 실제 VoiceOver의 두 번 탭과 음성 출력. 시뮬레이터에는 VoiceOver가 없다. 확인한 것은 접근성 트리와 AXPress까지다.
- 구 아키텍처 iOS 바이너리(스토어 빌드). RN 소스로는 같은 규칙에 걸리는 것을 확인했지만 실측은 못 했다.
- Android TalkBack 전부. 로컬에 Android SDK가 없다. 소스 기준 예측은 입력란 1개가 "초대코드" 수정창으로 잡히는 것이다. 입력한 뒤 이름과 값이 함께 읽히는지는 확인이 필요하다.
- 실제 앱 흐름(온보딩 → 코드로 참여하기). 컴포넌트와 props 형태는 실제 소비처(`JoinLogScreen`)와 같다.

  - Android TalkBack: 빈 값과 "AB" 입력 뒤 각각 이름("초대코드")과 값이 함께 읽히는지 본다. 이름이 빠지면 Android 한정으로 보이지 않는 placeholder나 `accessibilityLabelledBy`를 검토한다.

- **UX 백로그 후보(범위 밖, 수정 전부터의 동작)**:
  - 잘못된 코드일 때 입력란 아래 에러 문구가 화면 읽기 기능에 자동으로 안내되지 않는다(`JoinLogScreen.tsx:101-105`, 알림·실시간 영역 없음).
  - 6자를 채우면 키보드가 닫힌다(`Keyboard.dismiss`). 이때 VoiceOver 초점이 옮겨질 수 있다(미확인).
  - 입력한 코드가 입력란 값 한 덩어리로 읽혀, 글자가 묶여 들릴 수 있다(추정). 수정 전에는 요소 이름이 셀 글자를 공백으로 이은 "A B"였다.

## 5. 주의사항

- 숨김 입력란의 투명도는 0보다 크고 0.01보다 작게 둔다. 0이면 jest는 통과하지만 기기에서 입력란이 화면 읽기 기능에서 사라진다(iOS 실측, Android 추정). 0.01보다 크면 새 아키텍처 iOS에서 입력란이 틈 탭을 직접 받는다. spec이 양쪽을 막는다. 입력란을 투명도 0인 뷰로 감싸는 것도 막는다.
- 입력란 이름은 `accessibilityLabel`로 준다. `aria-label`로 바꾸면 jest는 통과하지만 기기에서 이름이 사라진다(spec이 막는다).
- 셀 숨김 속성을 행으로 옮기지 않는다. 새 아키텍처와 Android에서 행이 새 네이티브 뷰가 되어 틈 탭 경로가 바뀐다(spec이 셀마다 속성을 확인해 막는다).
- 감싸는 `Pressable`을 `View`로 바꾸지 않는다. 셀 탭 포커스가 사라진다.
- 시뮬레이터의 개발용 앱은 새 아키텍처라 스토어 빌드와 아키텍처가 다르다. 네이티브 층 동작을 시뮬레이터에서 확인했다면 이 차이를 함께 적는다.
- 검증에 쓴 임시 파일(루트 `metro.config.js`, 임시 검증 화면 폴더 `zz-codeinput-a11y/`, `.expo/`)과 임시 시뮬레이터 기기는 모두 삭제했다. 접근성 트리 덤프 도구와 픽셀 비교 스크립트는 저장소에 넣지 않았다.
