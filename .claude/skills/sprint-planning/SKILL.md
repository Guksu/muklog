# Sprint Planning — plan.md 작성 가이드

한 스프린트의 **단일 기능**을 개발자가 추측 없이 구현하고 QA가 교차검증할 수 있는 계획으로 만든다.

## 원칙 (왜)
- **TDD 기준으로 기획한다.** 각 인수조건은 곧 **테스트 케이스**가 된다. 인수조건을 "관찰 가능 + 테스트로 표현 가능"하게 쓰고, plan.md에 §테스트 케이스(정상·경계·실패 경로)를 명시한다. 단위 테스트/모킹 경계는 `docs/testing-strategy.md`를 따른다(SQL/RPC·외부 SDK는 모킹/스모크). developer는 이 케이스로 Red→Green→Refactor를 돈다.
- **1 스프린트 = 1 기능.** 범위가 좁을수록 인수조건이 명확해지고 QA가 경계면을 정확히 짚는다.
- **계약을 먼저 못 박는다.** 경계면 버그(API↔훅 shape 불일치 등)의 대부분은 계약 모호함에서 나온다. plan에서 shape을 확정하면 구현·검증이 같은 기준을 본다.
- **인수조건은 관찰 가능해야** 한다. QA가 "통과/실패"를 객관적으로 판정할 수 있어야 한다.

## 시작 전
1. `docs/design/architecture.md`를 읽는다 — 데이터 모델·화면·결정·비용 가드레일.
2. `docs/history/`(2026-09-01 이후)와 `docs/sprint/`(그 이전)의 이전 작업 기록을 훑어 의존성·중복을 파악한다.
3. **UX 개선 스프린트면** `ux-principles` 스킬을 읽고, `docs/ux/ux-backlog.md` 해당 항목의 위반 원칙 번호를 인수조건에 인용한다(개선이 관찰 가능해진다).

## plan.md 필수 섹션

```markdown
# Sprint: {기능명} ({slug})

## 1. 기능 한줄 정의
{이 스프린트가 끝나면 사용자가 무엇을 할 수 있는가}

## 2. 범위
- In-scope: {이번에 하는 것}
- Out-of-scope: {일부러 안 하는 것 — 다음 스프린트}

## 3. 데이터 · API 계약
- 테이블/컬럼 변경: {DDL 또는 기존 활용}
- RLS 정책: {필요 시}
- Edge Function / 쿼리 응답 shape: {필드명·타입까지 — snake/camel 명시}
- 프론트 훅 시그니처: {입력 → 반환 타입}

## 4. 화면 · UX
- 화면/컴포넌트 목록과 역할
- 상태: 로딩 / 빈 상태 / 에러 / 성공
- 원티드 토큰 사용 지점

## 5. 작업 목록 (각 인수조건 포함)
- [ ] {작업} — 인수조건: {관찰 가능한 기준} — 테스트: {이 인수조건을 검증할 테스트 한 줄}

## 5-1. 테스트 케이스 (TDD)
{인수조건별 정상·경계·실패 테스트 목록. 단위 테스트 대상(유틸/훅/화면)과 모킹/스모크 대상(SQL·RPC·외부 SDK) 구분.}

## 6. 엣지케이스
{빈 상태 · 권한/RLS · 동시성(커플 2명) · 네트워크 실패 · 입력 한계(사진5·인원2) · 인증(익명 만료·잘못된 코드)}

## 7. QA 교차검증 경계면
{생산자 ↔ 소비자 쌍 목록 — QA가 양쪽을 같이 읽을 대상}

## 8. 비용 가드레일 체크
{이 기능에 해당하는 것: Kakao 디바운스/캐싱 · 이미지 압축 · viewport 조회 · AWS 미사용}
```

## 작성 디테일
- **엣지케이스는 여러 각도에서.** 입력 경계(5장째/6장째, 2명째/3명째), 동시성(둘이 같은 먹로그 동시 편집), 실패(업로드 중 끊김), 인증(코드 만료/오타). muklog는 커플 동시 사용이 기본임을 늘 고려.
- **계약은 구체적으로.** "장소 정보" 대신 `{ place_name, kakao_place_id, lat, lng, road_address, category }` 처럼.
- **Out-of-scope를 분명히** 적어 스프린트가 부풀지 않게 한다.
- git 관련 작업은 plan에 넣지 않는다.

## 출력
`_workspace/{slug}/plan.md`(커밋되지 않는 인계물 — 보존 기록은 스프린트 종료 시 리더가 `docs/history/`에 종합). 인수조건마다 **테스트를 걸 공개 경계(seam)** 를 명시한다. 완료 후 developer에게 계약 핵심을 SendMessage로 전달.
